# T3-S3 LR1121: build and capture USB CRSF

This target ports the sniffer to the **LILYGO T3-S3 LR1121 non-PA** board
using ExpressLRS **3.5.6**. It receives **2.4 GHz LoRa** links, including
plain **500 Hz** on ExpressLRS 3.x. SX1280 FLRC modes **F500, F1000, D250
and D500** are incompatible with this LR1121 target; see the
[ExpressLRS 3.5.6 radio rate tables](https://github.com/ExpressLRS/ExpressLRS/blob/3.5.6/src/src/common.cpp).
Live aircraft telemetry and binary USB output have been verified on a
**T3-S3 LR1121 V1.2**, with **LR1121 radio firmware 1.1** and an
**ExpressLRS 3.x, 2.4 GHz, plain 500 Hz** link.

Use the **2.4 GHz antenna connector on the LR1121 module**. The board's
sub-GHz antenna connection is separate. The staged
[LR1121 hardware layout](../firmware/hardware/lilygo_t3s3_lr1121_sniffer_rx.json)
sets IRQ/DIO9 to GPIO36 and BUSY to GPIO34, with the radio's own RF switch
control. The integration uses a **10 MHz SPI clock**, retries the initial
radio probe, enables the required 3.0 V TCXO, and reapplies DIO9 interrupt
routing after radio configuration settles. During bring-up on radio
firmware 1.1, the chip received packets internally while its initial interrupt
routing produced no callbacks; reapplying the mask restored reception.
The SX1280 layout
is unsuitable for this board. Hardware references:
[LILYGO board documentation](https://github.com/Xinyuan-LilyGO/LilyGo-LoRa-Series/blob/master/docs/en/t3_s3_lr1121/t3_s3_lr1121_hw.md)
and [LILYGO LR1121 example](https://github.com/Xinyuan-LilyGO/LilyGo-LoRa-Series/blob/master/examples/LoRa/T3S3/LR1121_PingPong/LR1121_PingPong.ino).

## Windows build and flash

Run these commands from this repository in PowerShell. Use a **separate**
ExpressLRS checkout: the build script modifies its sources and configuration.

```powershell
python -m pip install platformio pyserial
git clone --branch 3.5.6 --depth 1 https://github.com/ExpressLRS/ExpressLRS.git ..\ExpressLRS-t3s3-lr1121
python firmware/build.py ..\ExpressLRS-t3s3-lr1121 --env T3S3_Sniffer_LR1121_RX_USB --phrase "your-binding-phrase" --upload-port COM27
```

Replace the example phrase and COM port with your link and board. The script
stages the hardware layout and binding UID, builds the firmware and filesystem,
then flashes **both**. Omitting `--upload-port` builds without flashing;
`--stage-only` prepares the checkout without compiling. The phrase and UID
are written inside the separate ExpressLRS checkout. LR1121 requires a primary
sub-GHz domain in ExpressLRS's build configuration; the script supplies EU868
while this target restricts scanning and hopping to 2.4 GHz.

The script runs firmware and filesystem targets separately. With the pinned
PlatformIO ESP32 platform, combining `-t upload -t uploadfs` selects only the
filesystem image and does not flash the application.

After flashing, unplug and reconnect the board if USB produces no data or
host writes time out. During bring-up, a watchdog reset after flashing restored
USB operation when the application was running but the USB endpoint was
unresponsive. PlatformIO's bundled esptool 4.5 does not offer that reset mode;
a power cycle is the practical recovery step with the supplied build tools.

| Environment | USB output | Consumer |
|---|---|---|
| `T3S3_Sniffer_LR1121_RX_USB` | Binary CRSF frames | `capture_crsf.py` or a binary CRSF application |
| `T3S3_Sniffer_LR1121_RX_Serial` | Readable diagnostics and `[CRSF]` hex lines | Serial terminal or existing Python GCS |

The `_USB` build disables ELRS debug logging and sends complete
`[address][length][type][payload][CRC]` frames. It drops frames when the USB
buffer is full so a disconnected or stalled host cannot block reception.
Synthetic LINK statistics are disabled in this build unless `GHOST_LINK_STATS`
is explicitly enabled. The current GCS serial reader expects the `_Serial`
format and does not parse the binary `_USB` stream.

Keep the target's USB flags unchanged. With the pinned PlatformIO board and
Arduino core, `USBSerial` is hardware USB Serial/JTAG and `Serial` is UART0.
Enabling `ARDUINO_USB_CDC_ON_BOOT` changes those names. See the
[PlatformIO board definition](https://github.com/platformio/platform-espressif32/blob/v6.4.0/boards/esp32-s3-devkitc-1.json)
and [Arduino USB declarations](https://github.com/espressif/arduino-esp32/blob/2.0.11/cores/esp32/HWCDC.h).

## Verify aircraft telemetry

After a full power cycle and USB reconnection, a simultaneous 30-second
comparison captured **503 CRC-valid aircraft frames** from the LR1121 sniffer
on COM27 and **503** from the SDR reference on COM19. All **503 frames matched**
by frame type and payload, ignoring destination address. Both streams had
**zero CRC failures and zero discarded bytes**, including capture boundaries.
Each contained 147 GPS, 146 attitude, 60 battery, 60 barometric altitude,
60 vario, and 30 flight-mode frames.

Close other applications using the port. List ports again if Windows assigns
a new COM number after flashing:

```powershell
python -m serial.tools.list_ports
python firmware/capture_crsf.py COM27 --duration 30 --output "$env:TEMP\elrs-capture.bin" --summary "$env:TEMP\elrs-capture.json"
```

The capture tool asserts DTR and leaves RTS low. It validates CRSF frame lengths
and CRC8/DVB-S2 (`0xD5`), recovers after noise or partial reads, and prints
decoded aircraft fields. `--quiet` hides individual frames; `--duration 0`
captures until Ctrl+C. `--output` preserves every USB byte, including noise.
Saved streams can be checked without a board:

```powershell
python firmware/capture_crsf.py --input "$env:TEMP\elrs-capture.bin" --quiet
```

Success requires `aircraft_telemetry_frames` greater than zero, with frames
such as GPS, battery, attitude or flight mode. **LINK-only output is not
telemetry success**: link frames can be locally synthesized without receiving
aircraft data. Exit status is `0` for verified aircraft telemetry, `1` for
none, and `2` for a capture/file error. A CRC-valid capture verifies transport
integrity; check decoded fields against the aircraft to confirm their origin.

If there is no aircraft telemetry, flash the `_Serial` environment to inspect
radio initialization, lock state and packet counters. Confirm that telemetry
is enabled on the live link, the phrase matches, the link runs ExpressLRS 3.x
in a supported 2.4 GHz LoRa mode, and the antenna uses the 2.4 GHz port.

The binary build also accepts `D\n` as an explicit troubleshooting command.
It replies with a text line containing readiness, connection state, packet
counts, and free USB buffer space, plus a radio version response if radio
initialization failed. Normal operation emits only binary CRSF;
do not send `D` while recording a stream that must contain no diagnostic text.
`P:<binding-phrase>\n` retargets a running receiver without reflashing.
